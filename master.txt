## Полное техническое задание на обновление сайта-приглашения Евы и Александра

Ты — арт-директор, UI/UX-дизайнер и frontend-разработчик. Не ограничивайся исправлением отдельных стилей. Пересобери композицию и контент сайта так, чтобы он воспринимался как самостоятельный премиальный свадебный проект, а не перекрашенная версия предыдущего сайта.

При конфликте с прежней реализацией приоритет у этого документа.

# 1. ЦЕЛЬ И ДАННЫЕ ПРОЕКТА

**Проект:** «Наша ночь».  
**Формат:** адаптивный одностраничный сайт-приглашение.  
**Количество основных секций:** ровно 8.

Все данные должны быть едиными в Hero, расписании, локации, форме, meta description и Footer. Не оставлять имена Анастасия и Кирилл, Анна и Михаил, а также англоязычное название площадки в пользовательском интерфейсе.

## 1.1. Ключевая задача редизайна

Цветовая концепция «почти чёрный + шампань + винный + айвори» сохраняется. Меняется логика дизайна и содержимое секций.

Не повторять композицию:
- фотография с подписью под ней;
- заголовок, затем абзац, затем изображение;
- стандартный вертикальный список расписания с фотографией сбоку;
- повторяющиеся карточки для расписания;
- изображение с подписью или названием поверх;
- стандартная форма из имени, присутствия, количества гостей и общего комментария;
- билет с именем гостя после отправки;
- английские названия секций и служебные подписи.

Новая композиция:
- Hero — кинематографическая обложка.
- История — крупный типографический манифест в паре с вертикальной фотографией свадебных деталей справа.
- Программа — редакционная вводная зона с фотографией интерьера и ниже четыре равные типографические колонки.
- Место — двухколоночная архитектурная сцена плюс схема территории.
- Дресс-код — редакционная композиция с текстом слева и фотографией фактур справа.
- Галерея — чистая сетка из четырёх фотографий без подписей.
- Ответ — интерактивный выбор и условные поля, а не обычная анкета.
- Завершение — типографический финальный экран.

Не использовать старый HTML как основу визуальной композиции. Можно сохранить семантические технические решения, но переработать структуру DOM и CSS под эту спецификацию.

# 2. ЖЁСТКИЕ ОГРАНИЧЕНИЯ

## 2.1. Язык

Весь видимый пользователю контент — только на русском языке:
- заголовки;
- навигация;
- кнопки;
- поля;
- placeholder;
- подсказки;
- подписи;
- названия точек карты;
- ошибки и подтверждения;
- текст в полноэкранном просмотре;
- alt-тексты;
- Footer;
- HTML title и meta description.

Не оставлять английские фразы вроде RSVP, STORY, LOCATION, AFTER PARTY, PRIVATE EVENT, FRAME, SCROLL, BLACK TIE OPTIONAL, DEMO PASS и подобных.

Названия файлов, CSS-классы, переменные, технические термины в коде и текст английских промптов для генерации изображений не относятся к пользовательскому интерфейсу и могут оставаться техническими.

## 2.2. Формат изображений

Все фотографии и растровые изображения — строго PNG.
- Не использовать WEBP.
- Не использовать AVIF.
- Не использовать JPG/JPEG.
- Не оставлять ссылки на файлы с этими расширениями.
- Не создавать новые фотографии в другом формате.
- Все используемые изображения должны находиться в assets/ и подключаться обычным путём.
- Не использовать data URI с изображениями.

Ориентиры:
- hero-couple.png — 2400×1350 px, желательно до 1,5 MB.
- venue-exterior.png — 1800×1200 px, желательно до 1,2 MB.
- dress-code-editorial.png — 1600×2000 px, желательно до 1,2 MB.
- фотографии галереи — 1200×1500 px, желательно до 1,2 MB каждое.

Не создавать чрезмерно крупные файлы. Если изображения уже оптимизированы и выглядят качественно, не пересохранять их без необходимости. Не жертвовать качеством ради формального уменьшения веса.

## 2.3. Полный запрет SVG

Искусственный интеллект, исполнитель и генератор кода не должны создавать:
- отдельные SVG-файлы;
- inline SVG;
- SVG-разметку в HTML;
- SVG-иконки;
- SVG-логотипы;
- SVG-карты;
- SVG-иллюстрации;
- SVG как временный или промежуточный формат.

Нельзя подключать библиотеку иконок, если она вставляет SVG в DOM. Для визуальной графики использовать HTML, CSS, псевдоэлементы и простые текстовые символы. Карта должна быть построена только средствами HTML/CSS.

## 2.4. Фотографии без подписей

Ни одна фотография не должна иметь текстовую подпись непосредственно под собой. Не использовать figcaption для названий, пояснений или нумерации кадров.

В галерее:
- никаких номеров кадров;
- никаких названий;
- никаких градиентных плашек;
- никаких текстовых оверлеев;
- никаких подписей снизу.

В остальных секциях фотографии располагаются рядом с текстом, а не под ним в формате карточки. Hero — единственное место, где заголовок намеренно располагается поверх фоновой фотографии.

Не добавлять подписи ради декоративного заполнения пустоты.

## 2.5. Нет визуальных пересечений

Запрещено добиваться дизайна наложениями:
- не позиционировать основной текст absolute;
- не использовать большие отрицательные margin;
- не накладывать заголовки друг на друга;
- не перекрывать текст фотографией;
- не фиксировать высоту блоков с переменным текстом;
- не обрезать длинные слова, имена, кнопки и подписи;
- не использовать transform для позиционирования текстовых блоков.

Абсолютное позиционирование допускается только для фонового изображения, фото-затемнения, декоративного номера, маркеров карты, линий и других неинтерактивных деталей.

Основной layout реализовать через CSS Grid и Flexbox. У grid-колонок использовать minmax(0, 1fr), у детей — min-width: 0. Для адаптивных размеров применять clamp().

- При выборе «Да, буду» показать условные поля и сделать транспорт обязательным.

- Для согласия заголовок результата: «До встречи, [имя]!».

- Показать сводку выбранных значений только для согласившегося гостя.
- Дать действие «Изменить ответ», возвращающее к форме.
- Не использовать localStorage, sessionStorage, fetch или сторонний backend.
- Не писать «ответ отправлен» или «сохранён». Указать: «Это демонстрация интерфейса: данные никуда не отправлены».

Desktop:

# 7. ТЕХНИЧЕСКАЯ РЕАЛИЗАЦИЯ

Стек текущего репозитория:

- styles.css;
- app.js;
- assets/.

Не добавлять фреймворк, сборщик, сервер, авторизацию, базу данных и API, если это не требуется.

## 7.1. HTML

- lang="ru".
- Семантические main, section, header, nav, footer, form, fieldset, legend.
- Одна H1 на странице.
- Логичная иерархия H2/H3.

## 7.2. CSS

- Цвета и шрифты хранить в :root.
- Общий контейнер через max-width и auto margins.
- Grid/Flexbox для композиции.
- Не использовать глобальные селекторы, случайно ломающие все кнопки или поля.
- Не задавать фиксированную высоту секциям с текстом.
- Использовать aspect-ratio для изображений.
- Для изображения — object-fit: cover и корректное object-position.
- Учитывать ширину содержимого, а не только viewport.
- Не использовать горизонтальный overflow для всей страницы.
- Крупные декоративные элементы не должны увеличивать фактическую ширину документа.
- Все состояния hover должны иметь keyboard focus аналоги.

## 7.3. JavaScript

- Не создавать искусственные задержки загрузки.
- Не требовать открытия приглашения отдельной кнопкой.
- Reveal через IntersectionObserver с fallback без него.
- При prefers-reduced-motion показывать элементы сразу.
- Навигация плавная, но доступная.
- Галерея поддерживает кнопки, Escape и стрелки клавиатуры.
- Фокус после закрытия lightbox возвращается к исходной кнопке.
- Форма обрабатывается только на клиенте; никаких сетевых запросов.
- Никаких ложных сообщений об отправке и сохранении.

## 7.4. Предотвращение наложений

- Основные блоки не позиционировать absolute.
- Не использовать отрицательные margin для наезда элементов.
- Не задавать текстовым блокам фиксированную высоту.
- Проверять переносы крупных заголовков.
- В grid использовать minmax(0, 1fr).
- На узком экране менять число колонок и порядок элементов.
- У фотографий заранее задавать пропорции, width и height.
- Для маркеров карты задавать позиции на каждом breakpoint.
- При тестировании не допускать наложения навигации на заголовок, заголовка на фото, маркеров на подписи и полей формы друг на друга.
